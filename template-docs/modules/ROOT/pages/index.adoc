= The template round trip
:page-type: concept
:page-docref: q4m2

A Thinkube template is an ordinary application repository. Not a scaffold, not a
generator, not a file tree full of placeholders — an application that runs. You
deploy it and get your own copy. You change your copy until it does something
useful. Then you publish it back, and it is a template again.

====

====

== Four movements, one shape

[cols="1,3",options="header"]
|===
| Movement | What happens

| *Create* | A template is written by hand, or published from an app that already works.
| *Instantiate* | The platform copies the template into your cluster and gives the copy a name, a database, a domain and an identity.
| *Improve* | You edit your copy and push. The pipeline tests it, builds it and rolls it out.
| *Publish* | Your copy is copied back out as a new template, which somebody else instantiates.
|===

The shape matters more than the steps: every arrow is a *copy*. Nothing is
rendered on the way in, and nothing has to be un-rendered on the way out. That
is the single decision the rest of this template's design follows from.

== Why business code carries no placeholders

The obvious way to build a template is to put `+{{ project_name }}+` in the
source and render it at deploy time. Thinkube deliberately does not, and the
reason shows up at the far end of the round trip.

Publishing an app as a template is a file copy. If the source had been rendered,
the published template would carry the *rendered* values — the first app's name
baked into the second app's template, permanently, unless something learned to
reverse the substitution. Reversing a substitution is far harder than never
making one.

So the platform draws a line:

* *Declarations and defaults live in the repository.* A template that forgets it
  needs a `model_id` is broken. Declarations belong to the application and should
  travel with it.
* *Values live in the deployment.* The name you typed, the domain, the database
  credentials, the secrets. They reach the app as environment variables and never
  enter the repository, so a published template cannot carry them.

Copier still runs when a template is instantiated, and the platform still passes
it `project_name` and friends. It just has nothing to substitute, because there
are no `.jinja` files in the business code. What Copier does here is copy.

== What is rendered, then

The Kubernetes manifests under `k8s/`. They are generated from `thinkube.yaml`
when the app is deployed, and regenerated by a pre-commit hook when you change
`thinkube.yaml`. They are the platform's output, not your source — which is why
publishing an app as a template leaves them behind.
