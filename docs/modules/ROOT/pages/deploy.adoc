= Deploy this template — a running task app of your own
:page-type: tutorial
:page-docref: w8k5

You will turn this template into a running application on your cluster, with its
own database, its own login, and its own address. It takes about five minutes,
most of which is the build. You need a Thinkube cluster and an account on it.

== Step 1: Deploy the template

There are three ways in. They all reach the same place — thinkube-control
deploying the same template — so pick the one that matches where you are.

=== Ask Claude

From code-server, in words:

[source,text]
----
Deploy the template https://github.com/thinkube/tkt-webapp-react-fastapi
and call it tasks
----

Claude calls the `deploy_template` MCP tool, and you can keep asking it for the
status as the build runs. This is the usual way to drive the platform.

=== Use the control panel

Open thinkube-control and go to *Templates*. The page lists every template in the
catalog. Choose one, give it a name, answer any parameters it declares, and
deploy. Use this when you want to see what is available rather than name a URL.

=== Start from the template's own page

Every published template can carry a deploy page, served by GitHub Pages from its
`docs/` folder. This template's is at
https://thinkube.github.io/tkt-webapp-react-fastapi/deploy.html[thinkube.github.io/tkt-webapp-react-fastapi/deploy.html].

Type your Thinkube domain and it sends you to
`https://control.<your-domain>/templates?deploy=<template-url>`, where the
*Templates* page opens with that template already loaded and waiting for a name.
Your domain is remembered in the browser for next time.

This is the route for someone who found the template on GitHub and has a cluster
of their own — the template advertises itself, and the deploy happens on the
reader's platform, not yours.

[NOTE]
====
The deploy page only exists if GitHub Pages is switched on for the repository,
with the source set to branch `main`, folder `/docs`. A template published from
your own app carries the page's files, but you enable Pages yourself.
====

=== Whichever route you took

The name you choose is the application's identity everywhere: its namespace, its
database, its Keycloak client, and its address. The deployment then starts in the
background and returns an id.

== Step 2: Watch the platform assemble the app

Ask Claude for the deployment status, or watch the *Deployments* view. The phases
run in order:

. *Setup and Copier* — the template is copied to `~/apps/tasks`. Nothing is
  rendered; see xref:index.adoc[The template round trip].
. *Resource gathering and creation* — namespace, TLS certificate, PostgreSQL
  database, Keycloak client, registry pull secret.
. *Git operations* — `k8s/` manifests are generated from `thinkube.yaml`, a Gitea
  repository is created, the code is pushed, and a webhook and an ArgoCD
  application are wired up.
. *Build* — the push triggers an Argo Workflow: backend tests, frontend tests,
  then container images for amd64 and arm64.
. *Rollout* — ArgoCD syncs the manifests and the pods start.

A test failure stops the build, and the deployment fails with it. That is the
intended behaviour: a template whose tests do not pass does not become an app.

== Step 3: Open your app

Go to `https://tasks.<your-domain>`. Keycloak asks you to sign in, then the app
loads: a sidebar, a task list, and the theme and language controls in the top
bar.

Two things to notice, because you did not configure either of them:

* *You were logged in.* The template speaks OAuth2 to the Keycloak client the
  deployment created for it.
* *The sidebar says "Tasks", not "Web Application".* The deployment named the app
  and the app read that name at runtime. See
  xref:variables.adoc[How configuration reaches your app].

Create a task. It is stored in the PostgreSQL database the deployment created,
under your user id.

== What you have now

A full-stack application that is *yours*: the code is checked out at
`~/apps/tasks`, pushed to Gitea, built by the cluster and served on your domain.
